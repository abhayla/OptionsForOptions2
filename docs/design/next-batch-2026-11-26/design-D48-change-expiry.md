## Core / Proof
Core: ONE edit `control: "expiry"` through POST /api/strategies/leg-edit, answered by the same reply as step/Shift, and passed through `door.admitMoved` before `legs.value` changes.
Proof (smallest real input, first step before other code): recorded condor fixture `frontend/tests/fixtures/outcome-condor.json` (SELL 22800 CE, BUY 23000 CE, SELL 22400 PE, BUY 22200 PE; used by leg-door-phase5.test.js:1-5) plus the recorded instrument file: call `edit.change_expiry(Listing, "NIFTY", legs, index=0, expiry=<next listed>)` and read back (a) the leg is the same strike/type/action/lots on the new expiry, (b) a target expiry that lacks 22800 CE returns the refusal and moves no leg. A failing core stops the build (evidence-and-proof E3).

## Where the control belongs
- Per leg: the expiry chip of each option leg row (`LegList.vue:223`, `data-testid="leg-expiry"`, today a read-only span) becomes a tappable chip that opens a native select of the underlying's listed expiries (same list as the picker: GET /api/catalogue/{u}/expiries, `backend/ofo_app/routes/catalogue.py:95`, with days-left per expiry, REQ-135 AC-2). Phone: the chip already sits on line 1 of the row (`LegList.vue:317` comment); a native select gives the OS picker, no new layout; keep the chip's h-8 but give the select a 44px tap area via padding, 16px gutters untouched.
- All legs: one "Expiry" select beside Shift / Width / Hedge (StrategyControls.vue, not read; confirm), sending the same request with `index` absent. This is the usual roll ("move the whole condor to next week") and avoids leaving a calendar by accident. Recommend BOTH in one request shape; if owner wants one, per-leg first.
- Options only in V1: a futures leg has no stepper (`legEdit.js:62` canStep, REQ-076 AC-1) and no expiry chip action; "all legs" with a futures leg is refused with a reason (not silently skipped, nothing moved).
- Spec basis: REQ-078 AC-7 (`spec/requirements/REQ-078.md:~83`: a move "never changes ... expiry") is departed from for this control only: SPEC CHANGE, new REQ-078 AC-11 (Expiry control: absolute, user-chosen date from the listed expiries, same strike and type, same side and lots) and AC-7 reworded "except AC-11". REQ-076 AC-1 (strike list per expiry), REQ-080 AC-1 (expiry list), REQ-135 AC-2 (days), ADR-319 (1), ADR-328 (1), ADR-008.

## Through the one door
- Move kind: new absolute `expiry` control. NOT in RELATIVE_CONTROLS (`legEdit.js:55`, which coalesces clicks into `steps` and keys `moveKey` `legEdit.js:59`); add `MOVE_CONTROLS = [...RELATIVE_CONTROLS, 'expiry']` and add `expiry: ['expiry']` to CONTROL_FIELDS (`legEdit.js:40-51`; `index` is optional for expiry, so buildEditRequest `:73` needs one rule: index present = one leg, absent = all). `editLeg` already sends non-relative edits straight to `sendEdit` (StrategyBuilderPage.vue, `editLeg` near :961), so no coalescing path is touched.
- Door: `sendEdit` gates `door.admitMoved(baseLegs, landed)` on `RELATIVE_CONTROLS.includes(edit.control)` (StrategyBuilderPage.vue:~996-997); change that one test to MOVE_CONTROLS. `admitMoved` (`useLegDoor.js:~42-58`) already compares each landed leg's `instrument_id` with the base leg's, and an expiry change changes it, so ADR-319 (1) same-contract ("Increase quantity / Keep separate / Cancel") and ADR-328 (1) opposite-side ("Keep both / Cancel") apply with no door change. The guard `frontend/tests/leg-emitters-guard.test.js` ALLOWED list stays unchanged: the only assign is still `sendEdit` with `door.admitMoved(` (guard ALLOWED row `sendEdit`, DOOR_CALLERS row `door.admitMoved(baseLegs, landed)`); no new `legs.value =` or `emit('update:legs'` is added. The LegList chip only does `emit('edit', {control:'expiry', ...})` like `LegList.vue:226/230`.
- Request: `{underlying, legs:[...as sent], edit:{control:"expiry", index?:int, expiry:"2026-12-03"}, shift_total?, view, seq}`. The browser sends the date text it read from the server's expiry list; never a strike.
- Server (does the route already support it? No): `EditIn.control` Literal (`backend/ofo_app/routes/leg_edit.py:302-303`) has no expiry; `extra="forbid"` (:301) so it is a 422 today. Minimal change: add "expiry" to the Literal, field `expiry: datetime.date | None`, `needs["expiry"] = ("expiry",)` in `_control_has_its_fields` (:325-329), a branch in `apply_edit` (:569-586) calling a new `edit.change_expiry(Listing(cat, today), name, legs, index_or_all, expiry)` in `backend/ofo/strategy/leg_edit.py` (next to `_land`:107 and `step_strike`:123; reuse `Listing.strikes`:97, which already returns () for an expired expiry). It keeps strike, type, action, lots; finds the contract on the target expiry from the instrument file; returns `Moved(legs, moved)`. Then the existing route path runs unchanged: `_check_landing` tradable check (:597, fail closed), re-capture of every moved leg (:674), engine numbers in the reply (ADR-008: the page computes nothing), freeze check (:624), typed price lost on a move (REQ-078 AC-8). `_next_shift_total` (:608) must return None for "expiry" (strikes did not move, but the total described the old legs; "-" like AC-9). Gate: same `current` (today's list loaded) rule as `_controls` (:507-516): off with `leg_edit_list_not_loaded_today`. Note `_controls` turns Width/Hedge off for >1 expiry (:521); a per-leg change therefore turns them off with their existing reason, say so in the AC.

## Owner question (draft, for the question tool; one question)
Spec basis: SPEC CHANGE to REQ-078 AC-7 ("a move never changes ... expiry"); ADR-319 (1), ADR-328 (1), ADR-320 (6) (D-48 parked). Real case: owner's 23 Nov NIFTY iron condor (22800/23000 CE, 22400/22200 PE) rolled to the next weekly expiry, where a strike may not be listed.
"You change the expiry of a leg (or all legs) that is already in the builder. If the new expiry does not list that leg's strike, what should happen?"
- A (recommended): Refuse that change, say which strike is not listed, move no leg. You choose another expiry or remove and re-add. Why: matches REQ-078 AC-6 and ADR-003/ADR-150 (1) (the platform never places a strike for you).
- B: Move to the nearest listed strike and say so. Risk: platform-chosen strike, the Q211 legal hold on platform-placed strikes (REQ-079 AC-1) and a silently different position.
- C: Ask per leg ("22,800 CE is not listed for 3 Dec: use 22,850 CE / Cancel"). Risk: a platform-suggested strike again, plus a second question type.
Coordinator already directed fail-closed; this question is only the product confirmation, and the build does not wait on it for A.
