## How this was built

Everything below comes from the code on this branch, not from memory. Re-run: `node frontend/e2e/support/inventory-extract.mjs` (writes the JSON), `node frontend/e2e/support/inventory-extract.mjs --check` (exit 1 when the committed JSON no longer matches the code), `node frontend/e2e/support/inventory-counts.mjs` (counts, and a row-for-row check of this file against the JSON; `--write` refreshes the counts block above).

**Extraction rule (the JSON follows exactly this; a guard test can apply the same rule):**

1. *Routes.* Every entry of `routes` in `frontend/src/router/routes.js` (which builds the table from `nav.js`: seven sections, Account & Settings, the fixed routes, the catch-all). The script evaluates a copy of `routes.js` with the `orderPath` import stubbed, so nav.js stays the single list. A redirect-only entry has component `(redirect)`. A page component mounted at several paths (for example `PositionsPage` at two paths, `AlertsPage` at three, the placeholder at 15) lists its controls once under its first path; later paths carry `"sameAs"`.
2. *Components.* From each routed page file and from `App.vue`, every `.vue` file imported (static `import X from '...vue'` or `import('...vue')`, `@/` = `frontend/src`) whose tag is used in the template (any import when the template uses `<component :is>`) is followed recursively. A component reached from exactly one page belongs to that page. A component reached from two or more pages, or from the shell and a page, belongs to the pseudo route `(shared components)`. `AppLayout.vue` and what only it renders belong to `(app shell)`. A `.vue` file nothing reaches belongs to `(unrouted components)`.
3. *What counts as a control* (one row per template element, in source order):
   - **button**: `<button>`, `role="button"`, or `<component :is>` naming `'button'`;
   - **link**: `<a>`, `<router-link>`, `<RouterLink>`, `role="link"` or `"menuitem"`, or `<component :is>` naming RouterLink or `'a'`;
   - **tab** (kind name for role-based widgets): any element with `role="tab"`, `"switch"`, `"checkbox"`, `"radio"`, `"option"`, `"combobox"`, `"textbox"` or `"slider"`;
   - **field**: `<input>` (not `type="hidden"`), `<select>`, `<textarea>`;
   - **disclosure**: `<summary>`;
   - **form**: `<form>` that has `@submit`;
   - **dialog**: `role="dialog"` or `"alertdialog"`, `<dialog>`, and every `<Modal>` or `<Drawer>` usage;
   - **key**: any element with `@keydown`, `@keyup` or `@keypress` (any modifier) that is none of the above, and every `addEventListener('keydown'|'keyup'|'keypress'` in a `<script>` block. An element that is already a control and also has a key handler gets one row; the handler is listed in `handlers`;
   - **click**: any other element or component with `@click` or `@dblclick` (a div, span, li, `<ExitButton>`, an overlay).
4. *Label* = visible text of the element (nested text joined, `{{ expr }}` kept as written, so a dynamic label shows its expression, not its value), else `aria-label`, else `title`, else `placeholder`, else `name`, else the text of the enclosing `<label>`. `testid` = `data-testid`; a bound `:data-testid` is shown with its expression in backticks. `source` = repo path : line of the opening tag.
5. *IDs* are `<PREFIX>-<nn>` in source order within a route (page file first, then its components in import order). The prefix per page component is in `PREFIXES` in the extractor; an unknown page makes the script exit 1, so a new route cannot be added silently. IDs shift when a control is added above others; the guard should match on `source` file and label/testid, not on the number.

**Known limits of the rule.** It reads templates only. A control that a component draws from a render function (`h()`) or from a `v-html` string is not seen. A label made from a script constant (`{{ REVIEW_AND_ADD_LABEL }}`) is shown as the expression; read the constant for the words. A control that exists once in the template but appears many times at run time (a row action per strategy) has one row. Things that only exist in the browser (Chrome's Back key, the address bar) are not controls here; the owner's lists use them (rows 11 and 12).

**Coverage method and its limits.** For each control the script looks for its `data-testid` (static: the exact id; dynamic: the fixed part before the `${`, followed by an id, not a letter) or, for a control without a testid or with a dynamic one and a long static label, its label in a role/text query, inside one `it()` or `test()` block. A block counts as *acts* when the matching line (or the next two) calls `trigger`, `click`, `setValue`, `fill`, `check`, `selectOption`, `press`, `dblclick` or `dispatchEvent`, or a variable holding the element is acted on within 25 lines; as *asserts* when it reads text, attributes, classes, visibility or existence. Playwright specs count when the testid is unique in the app or the spec opens a route that renders the control; vitest files count when they import a `.vue` file that renders the control (the component itself or a page above it). Known gaps: a test that submits a form (`trigger('submit')`) does not count as clicking the form's Save button (so Settings "Save" is NONE although the form is tested); a test that reaches the control through a helper that builds the testid is missed; page objects are read only for the getters in `nav.page.ts`. "acts" is the stronger claim; an "asserts" row shows the control is rendered with that text or state, not that it works. A covered row names up to three tests; the full list is not kept here.
