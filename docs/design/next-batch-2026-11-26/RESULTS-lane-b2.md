## Decided for the owner
- (00:05) A repeat of the SAME key and SAME body is let through the block (it is the designed way to learn the first outcome, ADR-017); the durable key claim in the order's own transaction then stores once or replays, so the block and the key never store twice. Any other key or body stays refused while an outcome is unknown.
- Redis is a hint (item 2): a Redis outage no longer refuses a keyed order; the durable table decides; a table that cannot be read refuses.
- The block is per strategy, not per user: one open attempt per strategy. While a request runs, a second request for the same strategy (second tab, double click with another key) is refused with the unknown-outcome sentence, so this also serialises order requests per strategy; no money effect, a rare "try again" for the user.
- Window 120 s (`SETTLE_SECONDS`) applies to PAPER attempts only (the app's own database is the authority there). A REAL attempt (the Execute door; Zerodha is the authority, ADR-016 to ADR-019) NEVER closes by time (coordinator, 22:20; it did before this fix: red test, then fixed): it closes only by stored evidence (an execution plan or key row written since the attempt began) or when the user's outcome is recorded (`order_outcome.record_outcome`). The Return door is not guarded (it records an outcome); it does not close an open attempt in this build (the window and the stored-rows check do): listed under "For the owner lane".
- Code 590 for the new sentence (587 was taken by `real_position_open_refused`); if Lane B3 or R1 picked 590 the unique-code test fails on merge: renumber mine.
- The exit and trigger doors keep their own refusals; the block runs before them (a refused exit during an unknown attempt reads the unknown-outcome sentence).
