# Builder brief: #338 (closing basket never blocked by a negative balance) + #353 (Kite allow-list per calling module) - GC-2h item 3a, Tier A

Common brief: docs/process/builder-brief.md
Core: a reduce-only (closing) basket that Zerodha says needs 0 or negative margin is never blocked by the margin gate,
even when the account's balance is negative; and a Kite read is allowed only from the module listed for it.
Proof: the real closing reply `tests/fixtures/kite_replies/margins-basket-exit-150717.json` with the account's
available funds set to -Rs 120.50 -> the EXIT basket passes the margin gate; an ENTRY basket with the same funds is
blocked; a module not on the allow-list calling a listed read -> refused with the existing refusal.
Spec basis: REQ-055 AC-1, AC-3; REQ-063 AC-1; ADR-012; #338; #353.

REQ-055 AC-3: "The platform's own margin figure is shown as a planning estimate; Zerodha's figure is authoritative."
Copy from: none - fixes in existing modules (backend/ofo/execution/margin_gate.py, backend/ofo/broker/kite_http.py, backend/ofo/broker/kite_endpoints.py).
Class: #338 - every reduce-only basket (exit, partial exit, buy-back) checked while the balance is <= 0, before 0 of them pass, after all; #353 - every Kite read call site, before any module may make any listed read, after only its listed module.
Findings checked: margin-gate-blocks-closing-basket, guard-as-forbidden-list, guard-without-killing-test, caller-supplied-verdict-trusted

## What to build
1. #338: the closing basket rule stated as an allow-list: a basket every leg of which reduces a held position and whose
   Zerodha-reported required margin is <= 0 passes, whatever the balance; any other basket is checked as today. Test
   with the real closing reply and a derived negative-funds account reply; an entry case and a mixed basket (one leg
   opens) stay blocked.
2. #353: `check_call` takes the calling module's identity from the call site the platform controls (an explicit
   argument passed by each door, checked against a closed map `{call: {module, ...}}` in kite_endpoints.py), never from
   caller-supplied text it cannot verify; every existing door passes its identity; a repo_scan test proves every call
   site passes one and the map lists only real modules.

## Attack cases
1. Mixed basket (close one leg, open another) with negative funds -> blocked.
2. Zerodha reports a positive margin for a closing basket -> checked as today.
3. A new module calling `fetch_positions` without being listed -> refused; the scan fails on a call site without identity.
4. Mutation: delete each new guard and name the killing test.
