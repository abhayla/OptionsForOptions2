# Part A: The whole project, core first

Core: real option prices → engine → screen → an order through the user's own Zerodha account → Zerodha's
confirmation → reconcile → watching against the user's rules.
Proof: Stage 4. First a throwaway script on the owner's own account (live quotes for 3 NIFTY + 3 SENSEX options,
basket margin), then one real small order confirmed by Zerodha and reconciled, then one real rule firing. Stages 0-3
are research and spec work that decide what the core must obey. They write no product code. Nothing outside the
core is built before the core gate passes.

## A0. What the product is, in one chain
`spec/vision/vision.md` and ADR-001/002/008/009/016/017 describe one chain:
1. Real NIFTY/SENSEX option prices come in.
2. One engine turns a strategy into payoff and P&L at every market level.
3. The user sees it and presses Execute Strategy.
4. The orders go out through the user's own Zerodha account.
5. Zerodha confirms them, and we reconcile against Zerodha's positions.
6. The strategy is watched against the user's rules: an alert plus prepared orders, never automatic.

**This chain is the core.** Sign-up, trials, referrals, the guided builder, the option chain screen, adjustments,
payments and the learn section exist to make it usable, sellable or legal.

## A2. How "nothing missed" is enforced, not just promised

1. **A coverage register.** `docs/process/coverage-register.md` is generated by a small script,
   `scripts/orchestrator/coverage.py`. It lists, from the files themselves:
   - every REQ-001..071 with each acceptance criterion;
   - every ADR-001..050;
   - every open question (Q204, Q205, Q258 and the "Open areas" list), plus the vendor enquiries;
   - every open GitHub issue (#30, #43, #45, #63, #89, #107, #110, #112, #115, #116);
   - every work item that is not done (W-008, W-009, W-011, W-017, W-024);
   - every hypothesis H1-H11;
   - every build-plan item (P0-P6, including the P3b and P4 copy rows) and every HANDOVER open item.

   Each row names the stage that closes it. **A requirement whose acceptance criteria fall in different stages is
   placed per acceptance criterion**, not as a whole. Its `--check` fails if any id or acceptance criterion is
   missing or unassigned. New REQs, ADRs, F-ids and Qs must be added, or the check fails.

   How it runs within the repo rules:
   - the script is project code under `scripts/orchestrator/` (allowed) and gets its own tests;
   - the check runs in a new project workflow `coverage.yml` on every PR. It is not added to the kit's `ci.yml` or
     `ci_local.py`, which are kit-owned;
   - the generated register is regenerated only in batched docs PRs (run-discipline C2), never inside feature PRs.

   It is a Tier B change.
2. **A full read, not a skim.** At the start of Stage 0, every REQ file (71), every ADR (50),
   `spec/open-questions.md`, `spec/testing/core-invariants.md`, `spec/data/domain-model.md`,
   `spec/business-rules/scenario-calculations.md`, `spec/technical-design/*.md` and `legacy-reuse.md` are read in
   full by 3 parallel read-only agents. Each returns, per file, its ACs, its open gaps and its conflicts with other
   files. I re-check every conflict they report against the source before recording it. Results go into the
   coverage register's "gaps" column, and a conflict becomes a finding or a Q.
3. **Gates per stage.** No stage starts before the previous stage's gate has passed, with evidence.
