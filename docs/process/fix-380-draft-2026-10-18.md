### Two related observations outside #380's AC list (each needs its own `deferred` issue, run-discipline B7)

- **Exit order, Q238 (owner decision in REQ-058):** "buys back the short legs first, then sells the long legs, and never
  mixes the two in one batch". The basket exit legs are `sorted(held.items())` by contract id (`execute_plan.py:218-221`)
  and go into ONE basket in that order (`ofo/execution/basket.py:247-250`, "in plan order"). For a multi-leg strategy
  that holds shorts and longs, buy-backs and sells share one basket. GC-3's 1-leg run is unaffected.
- **Entry order:** the entry plan is the stored definition's leg order (`routes/execute.py:351-353`), and
  `ofo.execution.sequence` ("protective legs first", REQ-056 / W-022) is not reachable (section 0). Checked by the
  review against REQ-056: AC-3 puts protective legs first, and AC-4 says "If a protective leg fails, the sell leg that
  depends on it is not submitted" - one basket cannot meet AC-4 (the same shape as Q238).
- Neither can affect GC-3L's 1-lot single-leg run: each basket holds one order (review, attack 6).

## 2. Options

Every option below is reads plus a basket built only on the user's click. None places, retries or substitutes an
order automatically (ADR-016..019, REQ-073 AC-4). Every option is **Tier A** (ADR-106 item 3: order state,
reconciliation, money, and any module the Execute/return routes import). Sizes are rough product lines, excluding
tests.

### (A) Wire `ofo.reconciliation` and `ofo.execution.partial` into the routes as they are

- **What changes for orders/money:** blocking follows `compare` (a surplus on a held contract blocks, AC-4; shared
  contracts block every holder, Q224; expired legs settle, ADR-083). Mismatches are stored and stay until a recorded
  resolution (Q222). The four partial choices call `partial.*`.
- **Blocker:** `partial` cannot be wired as it is. Its send path is `submit_confirmed` -> `_BrokerSink`, an API
  order send (`partial.py:912-959`); `Preparation.orders` (`partial.py:443`) is also an output, but it is built on
  the OrderBook and `OFO` tags below. ADR-054 forbids that ("the platform's server does not send orders through the
  API"), and REQ-073 AC-4 makes it a test failure. It also prices close orders at LTP (`partial.py:37`, OD-e) where the
  basket path prices from depth (ADR-080 (3)). It also keeps its state in the in-memory `OrderBook` with `OFO`+9-digit
  client tags (`partial.py:45`, OD-k), while the basket path uses stored plans and `OFS{s}V{p}L{l}` tags (ADR-105).
  So for partials, "wire as is" turns into a rewrite of partial's send half, which is option C.
- **Size:** about 1,500-2,000 lines (a StrategyRecord-from-database adapter, a migration, triggers, resolution routes,
  a screen, and the partial send-half rewrite).
- **Risk:** high. The two domain models (StrategyRecord + OrderBook vs stored plans + net-of-fills) would both have to
  stay true at once, and the gap between them is where this finding class came from.

### (B) Re-specify the ACs to what the Kite-basket path does today

- **What changes for orders/money:** nothing in code. The spec drops or narrows REQ-060 AC-1..7 and REQ-058 AC-1/2/4/6
  (SPEC CHANGE to Q196-Q199 and Q222/Q224, which the owner confirmed on 2026-09-29).
- **Size:** about 0 product lines; spec edits only.
- **Risk:** high, and it is the user's money. A change made in Kite (broker 150 vs platform 75) stays unblocked. Two
  strategies on one contract both execute after a Kite square-off. A rejection shows no reason. #380 states the risk:
  "Real money is at risk once a user acts in Kite directly or runs two strategies on one contract." It is acceptable
  only for a single-strategy owner-only V1, and the owner would have to say so.

### (C) Mix (recommended): wire the reconciler; make partial handling basket-native; re-specify only what the basket path makes impossible

- **Reconciliation:** one app adapter feeds `compare` with every strategy's held net (`execute_plan.held_units`, ADR-105)
  plus a standalone map. Both routes call it, so they stop disagreeing (AC-7 / Q224). Mismatches are stored and the
  block is sticky (migration, its own PR). Resolutions are recorded through `resolution`'s rules, adapted to the
  database. Triggers are reads only (section 4, T4).
- **Partial:** Complete Strategy / Retry Failed Leg = a NEW basket (new plan number) for exactly the unfilled
  remainder of the partial plan, priced fresh from depth. This is what ADR-079 already decided: "Repricing an unfilled
  remainder is offered ... through Complete Strategy (REQ-058 AC-4), as a new basket at a fresh price". Close Partial
  Strategy = the existing EXIT of the net, split shorts-first into two baskets (Q238). Review Manually = state plus
  Zerodha's reasons, nothing prepared. AC-1 numbers come from the one engine on the held net plus Zerodha's margin
  read. The rejection reason is shown (AC-6). `partial.py`'s pure rules are reused where their inputs fit; its send
  half is not wired.
- **Re-specify (only if GC-3L confirms):** REQ-073 AC-5's "placed only on the owner's own account" cannot be enforced
  by code on the basket path (section 1). This one is an owner question (Q-B3).
- **Size:** about 1,600-1,900 lines. Split as stacked Tier A PRs under the ~1,000-line cap (CLAUDE.md fast-delivery
  6): (1) migration (stored mismatch, sticky block, standalone); (2) reconciler adapter + both routes + triggers;
  (3) partial actions + reason + screen.
- **Risk:** medium. More blocks than today, by design: a user's own Kite trade on a strategy's contract now blocks that
  strategy until it is resolved (AC-4, Q222). Migration on the shared PostgreSQL. App-start / reconnect reads need a
  live Kite session, which expires daily (Q205).

- Business call: (B) removes protections the owner confirmed (Q222, Q224) and changes what a user sees and risks.

**Q-B2: What a user sees when a basket comes back partly filled (the partial choices under ADR-105).**
- Business call: it is what a user sees and can press on a partly filled real order.
- Settled already: REQ-058 AC-2 gives the four choices in order. ADR-079 makes Complete Strategy a new basket at a
  fresh price. The gap is a partly filled **EXIT**: AC-2 does not say whether an exit gets the same four.
- Options: (A, recommended) entry partial -> the four AC-2 choices in order; exit partial -> "Complete exit" (a new
  basket for the rest of the net) and "Review manually" only. Retry and Close Partial add nothing to an exit: closing
  a partial exit IS completing it. (B) the same four buttons for both. (C) no choices on an exit; the user presses
  Exit again.
- Why (A): a user whose exit is half done wants out. Two buttons that do the same thing invite a double press.
- Real case: none. The only real exit (2026-10-16, OFS1V2L0, SELL 65) filled 65/65.
- Spec basis: REQ-058 AC-2, AC-4; ADR-079 ("through Complete Strategy (REQ-058 AC-4), as a new basket at a fresh
  price"); ADR-105 ("an exit closes exactly that net"); REQ-018 / ADR-037 ("full or partial exit, all legs together").
  Spec silent on partial-exit choices (searched: partial exit, partially executed, Complete Strategy).

**Q-B3: Which manual-reconciliation actions the first screen offers (REQ-060 AC-5).**
- Business call: product scope of a screen users act on with real positions.
- Settled already: Q198's four actions, "*Adopt actual broker position · Review and modify strategy · Close/
  reconcile through a prepared order · Mark as requiring attention*; no casual 'ignore'; audited". Q222: the block
  lifts only through a recorded resolution. Q224: a shared contract refuses guess-based fixes. Open: product scope of
  the first release of the screen.
- Options: (A, recommended) first screen = "Close/reconcile through a prepared basket", "Mark as requiring
  attention" and "broker flat -> exited"; "Adopt" and "Review and modify" in the following contract. (B) all four
  at once.
- Why (A): "Adopt" on the basket path writes units into a strategy that no tagged fill explains, and "Review and
  modify" needs the versions screen. Both are larger and riskier. The three in (A) are enough to lift every block a
  Kite-side change can cause.
- Real case: none recorded. No mismatch has blocked a real strategy yet; the 2026-10-16 replies close 0 mismatches
  (F-42).
- Spec basis: REQ-060 AC-5; ADR-018 Q198; Q222; Q224; ADR-054 (a prepared order = a basket the user places).

**Q-B4: REQ-073 AC-5 on the basket path: which control counts as "placed only on the owner's own account".**
- Business call: it is the Zerodha/NSE compliance boundary (Q259). A legal/compliance criterion belongs to the owner.
- Fact: the basket form carries no account (`basket_post.py:89-91`). The platform cannot stop or see a basket placed

  exists. Whether Kite's basket accepts any account pin is **unverified**; check with the `zerodha-expert` skill

- Real case: GC-3L Monday runs under rule 4 (one private window, user id checked by hand).
- Spec basis: REQ-073 AC-5; ADR-060; ADR-090; ADR-108 (1) rule 4; Q259.

## 4. Technical calls I would make (decisions, with reason; the owner is not asked)

- **T1 Platform side = stored plans' net.** `compare` is fed with `execute_plan.held_units` per strategy (ADR-105: "the
  NET of Zerodha's filled quantities over ALL its stored plans"), never a second position model. `compare` takes
  `StrategyRecord`s (`compare.py:399-420`). The builder's step 1 (core proof) is to show `compare` gives the F-42 real
  cases' answers from a held-units adapter, on the recorded 2026-10-16 replies, before anything else is built.
- **T2 moved to the owner as Q-B5** (review 2026-10-18, finding 1): whether a surplus on a held contract blocks is
  what the user sees, and main reads it the other way on purpose.

**Q-B5 (clarification of REQ-060 AC-4 vs AC-7): does a user's own extra Kite position on a contract their strategy
holds block that strategy?**
- Business call: it decides when a user's real strategy is blocked by a trade they made themselves in Kite.
- Two readings exist. AC-7: "Reconciliation compares Zerodha's net quantity per contract with the strategy legs plus
  the recorded standalone quantity" and "A mismatch blocks only the strategy whose contract quantity disagrees" -> an
  unrecorded surplus disagrees, so it blocks; its example clears x 75 only with "standalone x 25" recorded. Main reads
  it the other way on purpose (`execute_plan.py:15-17`, `:233-243`: a surplus "beyond" the strategy blocks nothing),
  leaning on AC-7's "A broker position in no strategy and not recorded as standalone ... blocks no strategy".
- Options: (A, recommended) a surplus on a held contract blocks until the user records it as standalone or resolves it
  (AC-7's comparison rule; AC-4; Q222). (B) a surplus blocks nothing; only a shortfall blocks (main today).
- Real case: none recorded (F-42's broker 150 vs platform 75 is from the replayed fixtures).
- Spec basis: REQ-060 AC-4, AC-7 (quoted above); ADR-018 (Q197's example is a shortfall); Q222.
- **T3 One reconciler for both routes.** The Execute route must count the other strategies' units the way the return
  route does (Q224). One function, two callers: this removes today's disagreement between `routes/execute.py:495-506`
  and `routes/execution_return.py:185-204`.
- **T4 Triggers are reads only.** After execution = the return route. App start = lifespan, after the live session.
  Reconnect = the login hook (`live_market.py:296`). Page load of a strategy = ADR-079. Periodic waits on Q205
  (already open). Order events via the websocket order feed (F-07) come in a later item. A trigger never builds a
  basket.
- **T5 Sticky block and mismatch record in the database.** New table(s), with the migration in its own PR. The block
  lifts only through a recorded resolution (Q222). It gets its own audit event type, not `reconciliation_recorded`
  with Kite keys (`audit_allowlist.py:50-54` says why).
- **T6 Expired legs through `settlement` / ADR-083,** so an expired held leg is settled, not "missing".
- **T7 Partial actions are basket-native.** Complete/Retry = a new plan number for exactly the partial plan's unfilled
  remainder, priced from depth (ADR-079, ADR-080 (3)), refused while any order of the strategy is open (ADR-105
  one-open-plan). This narrows ADR-105's "a new entry is refused while it is not zero" for the remainder of the SAME
  plan only. It is recorded as a clarification row on ADR-105, a technical ADR by its own provenance. `partial.py`'s
  `submit_confirmed` / `_BrokerSink` are not wired (ADR-054, REQ-073 AC-4).
- **T8 Exit baskets shorts-first (Q238).** Two baskets: buy-backs first; the sells are offered only after Zerodha
  shows step 1 terminal. This fixes the observation in section 1.
- **T9 Rejection reason is shown, not stored raw.** `status_message` is read for the reply, length-capped. The audit
  keeps dropping it (`audit_allowlist.py:39-40`: free-form broker text).
- **T10 Detection upgrade for the class** `verified-on-a-module-the-product-does-not-call`. Add a `repo_scan` test that
  runs the transitive import trace from `ofo_app.main` and fails when a module that the evidence of a Verified
  requirement exercises is unreachable. Every work item of the next contract names REQ-058/060's ACs in its own
  `tests_required`.
- **T11 Delivery:** all Tier A, fresh Opus per PR, at most 2 rounds, stacked under ~1,000 lines each, migration alone.
  The ADR-108 operating rules stay in force for every live step until a verifier passes on main per AC (ADR-106
  item 3).
