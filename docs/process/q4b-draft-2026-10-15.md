# Stage 4b questions - draft (Q263-Q270)

Drafted 2026-10-15 for the orchestrator. Areas from master plan D7 (4b) and spec/open-questions.md, Open areas with no
question yet. Each question: what the spec already settles (verbatim, id first), the gap, a real case from the Kite
captures of 2026-10-15, options (recommended first), and whether the answer is user-visible.

Captures used (all under docs/research/kite-proof-2026-10-07/):
- rest-2026-10-15-order/ (captured 15:10:06 IST, NIFTY spot 22,945.95, expiry 2026-10-19, a Monday): NIFTY26O1923550CE
  (exchange token 47185) and NIFTY26O1921900PE (47109), each lot 65, tick 0.05; quote, instrument, order_margin,
  basket_margin, charges for each.
- rest-2026-10-15/ (captured 11:48 IST, ATM 22,950): quote.json (10 NIFTY 19-Oct strikes with depth),
  charges_orders.json and margins_basket.json for a 1-lot iron condor (SELL 23150 CE @53.30, BUY 23350 CE @17.30,
  SELL 22750 PE @65.15, BUY 22550 PE @34.00), shape_portfolio_positions.json (net and day both empty),
  shape_orders.json (empty).

Two cross-cutting facts every question below rests on:

- ADR-054: "the platform's server does not send orders through the API"

- REQ-073 AC-1: "one Kite basket of LIMIT orders marked read-only"

So the platform never places, modifies or cancels an order itself; every order action happens on Kite's own pages.
Several 4b areas were written before ADR-054 and assumed our server sends orders; the gaps below are what remains
once that is taken into account.

## Q263 — timeout, cancel and repricing: when a basket LIMIT order sits unfilled (or the user never returns from Kite), what does the platform show and offer, given that it cannot cancel or modify orders itself?

**Already settled by the spec:**

- ADR-054: "the platform's server does not send orders through the API"

- REQ-073 AC-3: "a basket the user closed or only partly placed is handled as a partial execution (REQ-058), never retried automatically"

- REQ-058 AC-6: "V1 never resubmits a failed order automatically"

- ADR-050: "on a timeout look the order up by tag, never resend"

- REQ-058: "the Close preparation also lists a CANCEL request for each such order"

**Gap:**
1. An order the user placed on Kite that stays OPEN (limit not reached): how long until the platform flags it, and what
   it offers. Nothing in the spec names an age or an action.
2. Repricing the unfilled remainder: a new basket while the old order is still open would double the leg. The spec
   has no rule that the old order must be Cancelled at Zerodha first.
3. The user leaves Kite's page without returning to our redirect URL: the spec's reconcile triggers (REQ-060 AC-1)
   cover it only through the periodic run; no explicit look-up-by-tag on the next page load is named.
4. Wording conformance (not a new decision): the Q223 rule above was written when our server sent orders. Under
   ADR-054 a CANCEL request can only be an instruction to the user to cancel in Kite (a Kite basket places orders; it
   has no cancel entry - unverified, F-22 does not list one). The REQ-058 text needs that wording fix, like REQ-055
   got on 2026-10-15.

**Real case:** NIFTY26O1923550CE at 15:10:05 (quote_CE.json): bid 3.95 x 13,260, ask 4.00 x 65 (one lot only), next
ask 4.05 x 12,545; LTP 3.95. A BUY 1 lot LIMIT at the LTP (3.95) joins the bid queue behind 13,260 units and may not
fill; at 4.00 it takes the only lot offered. No real case of an open or partly filled order yet: shape_orders.json at
11:48 is empty.

**Options:**
- **A (recommended):** no timer and no in-platform cancel or modify. The strategy shows each open order with its age
  and Zerodha's status, read by tag on return from Kite, on every page load of that strategy, and on the periodic
  reconcile. The user cancels or modifies in Kite (a link to Kite's order book). Repricing the unfilled remainder is
  offered only after Zerodha shows the old order Cancelled (or Rejected), through Complete Strategy (REQ-058 AC-4),
  as a new basket at a fresh price. Why: it is the only option that keeps ADR-054 and REQ-058 AC-6 as written and
  cannot double a leg. Cost: one extra trip to Kite for every reprice.
- **B:** mark basket orders IOC (immediate-or-cancel) so an unfilled part dies at the exchange and never sits open.
  Consequence: no stale orders, but a thin leg partly fills far more often (with one lot at the ask, a 2-lot BUY fills
  1 lot and cancels 1), pushing more strategies into Partially Executed. Whether a Kite basket honours `validity`
  IOC is unverified.
- **C:** the platform cancels or modifies an open order through the API after the user confirms. **SPEC CHANGE**:
  ADR-054: "the platform's server does not send orders through the API"; and whether an API cancel or modify counts
  as an algo order under F-17 is unknown.

**User-visible:** yes (what the strategy screen shows for an unfilled order and what the user can do next).

Spec basis: ADR-054, REQ-073 AC-1/AC-3, REQ-058 AC-4/AC-6 and its Q223 section, ADR-050 item 4(a), REQ-060 AC-1,
F-07, F-22.

## Q264 — MIS/NRML (product type): which Zerodha product does every basket order carry, and can the user choose it?

**Already settled by the spec:** nothing names a product type (searched: MIS, NRML, product type, intraday, carry
forward, square-off). Related lines:

- REQ-061 AC-3: "Once grouped, positions are monitored as a strategy."

- REQ-059: "reduce-only against the active positions"

**Gap:**
1. The product for entry and adjustment orders. Strategies are monitored across days (REQ-041..043); an MIS
   (intraday) position is squared off by Zerodha the same afternoon (the adjustment data contract row 19 records an
   unconfirmed 3.24 pm on expiry day), which would end a strategy the user meant to hold.
2. Exit orders: Zerodha keeps positions per product, so an exit must carry the product of the position it closes. A
   SELL NRML against an MIS long does not reduce it; it opens a new NRML short. REQ-059's reduce-only check has to
   compare product too. This matters for positions adopted through REQ-061, which may be MIS.

**Real case:** every 2026-10-15 capture (order_margin_CE.json, charges_CE.json, charges_orders.json) was requested
with `product` NRML, and Zerodha answered for NRML; no MIS request was captured. shape_portfolio_positions.json is
empty, so there is no real case of an MIS position on the owner's account (no real case in 1 day of captures).

**Options:**
- **A (recommended):** every entry and adjustment order is NRML, with no choice on screen; every exit carries the
  product of the position it reduces (taken from Zerodha's position row); the order review shows the product in
  words (Carry forward, NRML). Why: monitoring over days needs positions that survive the day, and one fixed value
  removes a beginner-level trap. Cost: a user who wants intraday-only must exit by hand.
- **B:** NRML by default, MIS selectable per strategy at the Advanced level, with an elevated risk message that
  Zerodha squares off MIS positions the same day. Consequence: a monitored strategy can be ended by the broker
  without a platform rule firing.
- **C:** the user picks MIS or NRML on every strategy. Consequence: a question beginners cannot answer, at every
  execution.

**User-visible:** yes (the product appears on the order review and decides whether Zerodha closes positions that
day).

Spec basis: none for the product itself (searched: MIS, NRML, product, intraday, square-off); constrained by REQ-059
(exit reduce-only), REQ-061 AC-3, ADR-018.

## Q265 — tick rounding: when a basket LIMIT price is computed (mid, tolerance, planned entry) and is not a multiple of the contract's tick size, which way is it rounded?

**Already settled by the spec:**

- ADR-050: "Lot size, tick size and freeze limit are per-broker data with dates"

- ADR-017: "picks valid order parameters per leg (allowed types, market-order limits, price bands, tick size, partial fills)"

- REQ-059 AC-4: "Validation never silently changes the user's strategy."

- ADR-068: "the mid of bid and ask when no LTP exists"

**Gap:** the rounding direction and where it happens. Depth prices are already on the tick; derived prices are not
(a mid, a per-leg limit split from a strategy-level tolerance). Also whether a price outside the day's circuit band is
clamped or blocked.

**Real case:** both captured contracts have `tick_size` 0.05 (instrument_CE.json, instrument_PE.json). Every depth
price in quote_CE.json and quote_PE.json is a 0.05 multiple. The mid of the CE touch (3.95 / 4.00) is 3.975 and of
the PE touch (4.55 / 4.60) is 4.575 - neither is a valid price. A half-tick on one lot is Rs 0.025 x 65 = Rs 1.625.
Bands: CE `lower_circuit_limit` 0.05, `upper_circuit_limit` 32.60; Kite also returns `high_limit_price_protection`
24.15, a field not in Kite's public docs (F-29).

**Options:**
- **A (recommended):** round every derived limit to the tick in the direction that never goes past what the user
  accepted - BUY rounds down, SELL rounds up - exactly in Decimal, in the engine, before the review is shown, so the
  review shows the price that will be sent. A price outside the circuit band blocks that leg with the reason, never a
  silent clamp. Why: REQ-059 AC-4 forbids silently making the user's terms worse; the cost is at most half a tick of
  fill chance.
- **B:** round toward the touch (BUY up, SELL down) to raise the chance of a fill. Consequence: the sent price can be
  half a tick worse than the user's stated limit or tolerance.
- **C:** round half-even (nearest tick). Consequence: direction depends on the number, so sometimes worse than the
  user's limit.

**User-visible:** no (the shown price moves by at most half a tick; the rule is internal mechanics).

Spec basis: ADR-050 item 2, ADR-017 Q28, REQ-054 AC-4, REQ-059 AC-4, ADR-068 item 1, F-29.

## Q266 — quantity edge cases (lots, freeze limits, slicing): how is a leg whose quantity is above the exchange freeze limit handled in a Kite basket, and what is the freeze limit's source?

**Already settled by the spec:**

- REQ-059: "No quantity cap beyond margin; Zerodha's own checks are the authority (ADR-016)."

- REQ-054 AC-4: "Lot size, tick size and freeze limit are stored per broker with the date the broker's list showed them."

- REQ-054: "Zerodha's list has no freeze limit"

- ADR-050: "at most 10 slices"

- ADR-054: "How many orders may one basket hold"

Also settled: quantity is units (lots x lot size), never lots (scenario-calculations section 1); exits must be a
multiple of the lot size (REQ-059 exit section).

**Gap:**
1. No freeze-limit value exists for Zerodha (its list carries none), so nothing today can tell that a leg needs
   splitting. ADR-050's 10-slice cap is about Kite's API autoslice, which the basket path does not use; whether a basket
   order accepts autoslice is unknown (F-22 gap).
2. Whether to split a large leg into several basket orders (each carrying the leg's tag) or refuse it.
3. A lot-size revision on a live contract (ADR-059 lets lot size follow the source): exit quantities for a position
   bought in the old lot. No rule.

**Real case:** lot 65 on both captured contracts (F-20: 65 on all 1,918 NIFTY rows of 6 Oct 2026). No freeze value
in any Zerodha capture; F-04 recorded 3,511 (Angel One) vs 3,510 (Upstox) for one NIFTY contract on 2026-10-02. The
golden test's 75 lot (scenario-calculations section 6) is the pre-revision lot - no real case of a live position held
across a lot change.

**Options:**
- **A (recommended):** one basket order per leg; a leg above the stored freeze limit is blocked at review with the
  reason and the limit; the freeze limit is loaded from the exchange's published freeze-quantity file with its date
  (REQ-054 AC-4); while no value is stored for a contract, the review warns that Zerodha may reject a large order.
  Why: keeps one order per leg (simple tag matching, simple partial-fill handling) for the retail sizes V1 targets.
  Note: adding the exchange file is a new external source - an owner call.
- **B:** split a leg above the freeze limit into several basket orders of at most the limit, same leg tag plus a
  slice number. Consequence: larger strategies work, but each slice can fill separately (more partial states) and the
  basket size limit is unknown (ADR-054 open).
- **C:** no freeze check; let Zerodha reject (ADR-016 pattern). Consequence: the rejection arrives after the user
  placed the other legs - a protective leg filled and a short leg rejected becomes a partial execution.

**User-visible:** yes (a large strategy is blocked or split on the order review).

Spec basis: REQ-059 gate decisions, REQ-054 AC-4 and its per-broker-values section, ADR-050 items 2 and 4(h), ADR-054
open items, ADR-059, F-04, F-20, F-22.

## Q267 — the charges model: where do the charges numbers on the order review, in P&L and in the max-loss sentences come from?

**Already settled by the spec:**

- ADR-071: "until the charges model is decided and the engine includes real charges"

- REQ-056 AC-8: "builds the order plan (leg, action, instrument, quantity, order type, price, sequence, margin, charges, broker warnings) without placing anything"

- REQ-059 AC-3: "charges estimate where available"

- REQ-032: "The engine exposes margin-planning and charges interfaces (IC §5)."

- ADR-016: "the platform does not rebuild Zerodha's risk rules"

- REQ-055 AC-3: "The platform's own margin figure is shown as a planning estimate; Zerodha's figure is authoritative."

**Gap:** the source (Zerodha's per-order figure vs our own rate table), whether expiry scenarios and max loss include
charges (ADR-071 says a new decision replaces the before-charges phrase), and what is shown with no Zerodha session.

**Real case:**
- charges_CE.json, 1 lot NIFTY26O1923550CE at 3.95: BUY total Rs 23.71 (brokerage 20, exchange 0.0912, SEBI 0.0003,
  stamp 0, GST 3.6165); SELL total Rs 24.09 (adds STT 0.3851 = 0.15% of the Rs 256.75 premium). Round trip Rs 47.80 =
  18.6% of the premium. charges_PE.json at 4.60: Rs 23.73 + Rs 24.17 = Rs 47.90 on Rs 299.
- charges_orders.json, the 1-lot iron condor entry: Rs 30.25 + 24.07 + 31.73 + 24.53 = Rs 110.59. Its credit is
  67.15 x 65 = Rs 4,364.75 and max loss (200 - 67.15) x 65 = Rs 8,635.25, so entry plus a similar exit (about Rs 221)
  is about 5% of the max profit.
- Observation to register: margins_basket.json's top-level `charges.total` is 0 while its own `brokerage` reads 20
  (both captures); only the per-order `charges` blocks are consistent. Also every amount arrives as a binary float
  (F-33), so it must be parsed as Decimal.

**Options:**
- **A (recommended):** Zerodha's `/charges/orders` reply is the charges figure, per order and in total, on the order
  review and for actual fills (the ADR-016 / REQ-055 AC-3 pattern: Zerodha's figure is authoritative, nothing to
  maintain when STT changes). The outcome view keeps ADR-071's phrase and adds one line under it: estimated charges
  to enter and exit at these prices, Rs X (Zerodha's figure), shown only with a Zerodha session; without one it says
  charges appear after connecting Zerodha. Realised P&L after fills is shown before and after charges. Why: one
  authority, exact, no rate table to drift.
- **B:** our own rate table in the engine (brokerage, STT, exchange, SEBI, stamp, GST as admin settings), used
  everywhere including drafts without a session, and max loss includes charges. Consequence: works signed out, but
  drifts whenever a rate changes (STT on option sells is 0.15% in this capture), and duplicates a Zerodha number.
- **C:** A for the review and fills, plus max loss and max profit stated after round-trip charges (ADR-071 phrase
  replaced). Consequence: honest net numbers, but the scenario table and the summary then use different bases unless
  every cell includes charges, which needs B's table for levels no order exists for.

**User-visible:** yes (charges numbers on the review, in P&L and in the money sentences).

Spec basis: ADR-071, ADR-016, ADR-008, REQ-032 AC-6, REQ-055 AC-3, REQ-056 AC-8, REQ-059 AC-3, F-33.

## Q268 — bid/ask/slippage: in Execute at current market conditions, what LIMIT price does each basket order carry, and how is slippage shown?

**Already settled by the spec:**

- REQ-056 AC-7: "the user picks 'Execute at current market conditions' or 'I want price protection' with a limit or a strategy-level price tolerance"

- REQ-073 AC-1: "one Kite basket of LIMIT orders marked read-only"

- ADR-068: "the mid of bid and ask when no LTP exists"

The live P&L formula uses the LTP (scenario-calculations section 2); its open note covers which price is used for
live estimates, slippage and charges.

**Gap:** with LIMIT orders only, current market conditions needs a concrete per-leg price rule; how the
strategy-level tolerance becomes per-leg limits; what the review shows as expected vs executable.

**Real case:**
- quote_CE.json (15:10:05): BUY 1 lot NIFTY26O1923550CE - planned at LTP 3.95 = Rs 256.75; executable at the ask
  4.00 x 65 = Rs 260.00; slippage Rs 3.25. For 2 lots the depth gives 65 @ 4.00 + 65 @ 4.05 = Rs 523.25 vs Rs 513.50
  at LTP (Rs 9.75).
- quote.json (11:48:10): SELL 23150 CE bid 53.25 / ask 53.45, LTP 53.20 (the LTP is below the bid); SELL 22750 PE bid
  65.10 / ask 65.30, LTP 65.30 - selling at the bid gives Rs 13.00 less than at LTP for 1 lot.

**Options:**
- **A (recommended):** current market conditions = for each leg, the worst price level in Kite's 5-level depth needed
  to fill the whole quantity (BUY: ask side, SELL: bid side), rounded per Q265, refused if outside the circuit band;
  if the 5 levels cannot fill the quantity, the review says so and offers price protection instead. The review shows,
  per leg and in total, planned (entry price), executable (depth) and the difference in Rs as slippage. Price
  protection = the user's tolerance split into per-leg limits. Why: a LIMIT at the touch is what Kite's own market
  order does in effect, and the user sees the cost before placing.
- **B:** LIMIT at the LTP or mid for every leg. Consequence: often does not fill (the CE above would sit at 3.95
  behind 13,260 units), sending users into Q263's open-order path.
- **C:** touch plus a fixed buffer of N ticks. Consequence: fills more reliably on fast markets but always pays the
  buffer, and N is a number nobody has measured.

**User-visible:** yes (prices on the review and the slippage line).

Spec basis: REQ-056 AC-7, REQ-073 AC-1, ADR-017 Q28, ADR-068 item 1, scenario-calculations section 2 open note,
F-29 (depth only in `depth.buy/sell`; 0 means absent).

## Q269 — expiry and multi-expiry execution: what happens to a strategy when one of its legs reaches expiry, and how is expiry-day entry treated?

**Already settled by the spec:**

- ADR-006: "each leg has its own expiry; payoff, margin, P&L, Greeks and execution engines support per-leg expiry"

- REQ-059: "the expiry has not passed"

- REQ-060 AC-2: "missing platform position, unexpected broker position"

- REQ-056 AC-6: "elevated → warn; exceptional → explicit acknowledgement"

Also settled: expiry dates come from the instrument list, never a weekday (F-05); Limited users' multi-expiry exits
(REQ-059 SPEC CHANGE item d).

**Gap:**
1. A leg that expires (cash-settled index option) leaves Zerodha's positions. Read literally, reconciliation sees a
   missing platform position and blocks the strategy. Nothing says expiry settlement is recorded as a settlement, at
   which price, and what state follows (calendar: continues with remaining legs; all legs expired: Exited).
2. Entering a contract on its own expiry day: allowed, warned or blocked. F-20 records the extra 2% ELM on short
   options and no calendar-spread benefit on expiry day, so margin can jump.
3. Exit near the close on expiry day: F-33 found expiring SENSEX options with candles until 15:39 while the engine's
   expiry close is 15:30 (unmeasured why).

**Real case:** the captured contracts expire 2026-10-19, a Monday (F-05 holiday shift pattern). F-33: SENSEX
26O0872500PE last candle 905.00 at 15:39 on 2026-10-08. No real case of a held leg expiring on the owner's account
(positions empty), and no settlement price captured.

**Options:**
- **A (recommended):** expiry is a recorded event, not a mismatch: after the expiry close, a leg whose contract has
  expired is closed in the platform at the exchange settlement price (to be read from Zerodha's position or the
  exchange file - source to verify), with a timeline entry; reconciliation expects that leg gone. A strategy with
  legs left continues (calendar); one with none becomes Exited. Entry into a contract expiring today is allowed with
  an elevated message naming the extra expiry-day margin; a short leg expiring today needs the explicit
  acknowledgement. Why: keeps ADR-006 per-leg expiry and stops every calendar being blocked the day its near leg
  expires.
- **B:** as A, but new entries in a contract on its expiry day are blocked. Consequence: safer for beginners;
  removes expiry-day strategies some intermediate users trade.
- **C:** the platform asks the user to exit a leg before its expiry and treats an expired leg as a mismatch to
  resolve by hand. Consequence: every calendar strategy blocks once per near expiry.

**User-visible:** yes (strategy state after expiry, expiry-day messages).

Spec basis: ADR-006 Q40, REQ-059 Q239 and exit sections, REQ-060 AC-2, REQ-056 AC-6, ADR-008 expiry close
(scenario-calculations section 4), F-05, F-20, F-33.

## Q270 — existing-position grouping (REQ-061): how does the platform suggest multi-leg structures from the positions it finds on connect, and what entry price does a grouped leg get?

**Already settled by the spec:**

- ADR-018: "Zerodha positions are discovered on connect and grouped only by the user."

- REQ-061 AC-1: "On connection the platform fetches open positions and identifies possible multi-leg structures."

- REQ-061 AC-4: "The grouping logic is explicit and auditable (every grouping decision recorded)."

- REQ-060 AC-7: "A broker position in no strategy and not recorded as standalone is offered the grouping choice"

- ADR-056: "the user picks which strategy absorbs the change"

- ADR-006: "never forces a template"

**Gap:** the suggestion rule (which positions are proposed together), the entry price written into a grouped leg
(Zerodha's average price, or the user types it), and how product (Q264) carries over.

**Real case:** shape_portfolio_positions.json (2026-10-15 11:48): `net` and `day` both empty - no real case on the
owner's account. The first real case will be the 4b order itself (BUY 1 lot, then exited the same day).

**Options:**
- **A (recommended):** one suggested group per underlying and expiry, legs listed with side, strike, quantity and
  product, named only as a resemblance to a template (ADR-006 Q52), never applied until the user confirms; the user
  can move any position between groups, to an existing strategy, or leave it standalone. A grouped leg's entry price
  is Zerodha's average price for that position, shown as From Zerodha and editable before confirming. Every choice is
  an audit entry. Why: one expiry per group matches what beginners hold; calendars are formed by moving a leg.
- **B:** one suggested group per underlying across all expiries. Consequence: calendars appear together, but
  unrelated positions on one index get lumped.
- **C:** no suggestion; a list the user groups by hand. Consequence: simplest, but REQ-061 AC-1 asks the platform to
  identify possible structures.

**User-visible:** yes (the grouping screen on connect and the entry prices of adopted legs).

Spec basis: REQ-061 AC-1..AC-4, ADR-018 Q24, REQ-060 AC-7, ADR-056 item 6, ADR-006 Q52, ADR-035 (entry price drives
expiry P&L).
