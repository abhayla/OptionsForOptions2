# W-058: Kite login callback and encrypted broker-token storage

- **Core / Proof:** see frontmatter. Step 1 is the domain lifecycle and the store on fakes; the live proof is one owner
  login, run after the token-expiry measurement.
- **Spec basis:** REQ-015 AC-6 (no password, PIN or OTP; authentication on Zerodha's side), AC-7 (about one day;
  expiry never deletes identity, strategies or entitlements), AC-9 (only the official secure token mechanism);
  REQ-063 AC-5 (broker credentials never stored beyond the official mechanism); core-invariants §4 (token encrypted at
  rest and never logged); ADR-020; ADR-053 (daily logout, visible pause).
- **Copy from:** legacy-reuse row 9 / `app/api/routes/auth.py:60-175` (REFERENCE: the flow only; the legacy stored the
  token in plaintext) and `app/utils/encryption.py` (REFERENCE: a dedicated key, not one derived from `JWT_SECRET`);
  `cryptography==46.0.3` pinned from algochanakya@bf9faf7 `backend/requirements.txt`.
- **Q210 (open):** whether each user brings their own Kite app is undecided, so the app's api key and secret come from
  one credentials source behind the adapter; V1 single-user (ADR-051) uses the platform's configured app.
- **Stated limitation:** login states live in one process's memory, so with several workers (or after a restart) a
  callback that reaches another worker fails closed as "expired or already used"; V1 runs one worker.
- **Stated limitation:** the login must start on the same host as KITE_REDIRECT_URL (localhost vs 127.0.0.1 drops the
  login cookie; the callback then fails closed).
