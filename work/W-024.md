# W-024: Error classification and user-facing error messages

An error catalogue with at least the AC-1 classes, each error carrying what happened, the impact, what is blocked and the next action (all four required), in calm decision-support wording (ADR-003).

- **Core:** Every error class produces a message with all four parts filled and no advice words.
- **Proof:** tests/errors/test_error_catalogue.py iterates every class, builds an example error and asserts the four parts are non-empty and free of banned phrases.
- **Spec basis:** REQ-065 and the decisions it cites; approved 2026-09-29 under ADR-045.
- **Decision (2026-10-08, orchestrator as product owner, round 9 part 2):** the timeline "why" text is not an error, so REQ-065 AC-2's four parts do not apply to it; it is platform wording, so it comes from the catalogue as a separate template kind `explanation` (fields: what triggered, the values seen, the rule) with the same wording check and the same pin file (ADR-003 Q226; REQ-065 AC-2 covers errors only).
- **Decision (2026-10-08, orchestrator as architect, round 9 part 6):** the no-free-text guarantee moves to the API boundary: an exception marked `ofo.errors.UserFacing` shows its render() four-part message; any other exception shows the INTERNAL_SYSTEM template with its own text only in the log, so text in non-UserFacing exceptions is developer detail by construction and the producer inventory counts only text that can flow into a UserFacing type, a label table or an explanation (run-discipline B8; REQ-065 AC-1/AC-2; ADR-003 Q226).
