# W-056: Re-key the instrument catalogue on the exchange identity

- **Core:** contracts identified by (exchange segment, exchange token); Zerodha ids only in the per-broker table; W-053 proofs
  still hold.
- **Spec basis:** REQ-054 AC-3 and AC-4 (added 2026-10-02); REQ-053 decision "one identity across brokers - SPEC
  CHANGE to the Q257 identity list"; ADR-050; spec/findings.md F-01..F-05, F-10 (this item first said (exchange, exchange_token); corrected, spec-adherence
  class 1).
- **Copy from:** none - algochanakya's symbol converter, token manager and per-broker token table are SKIP
  (spec/findings.md F-09; ADR-050 item 5).
- Finding `instrument-identity-keyed-on-one-broker` stays `unguarded` after this lands: the execution layer still links
  orders by Zerodha's symbol (issue #115, deferred from the W-056 review).
- **Decision (orchestrator, stage 2 brief, 2026-10-02):** current lot_size, tick_size, freeze_limit and broker_symbol
  live on the `broker_instruments` row; their history goes into the existing append-only `catalogue_term_changes`,
  extended with a nullable `broker` column (NULL = contract-level term such as expiry; 'zerodha' = that broker's term).
  One history table, the W-053 guard reused.
- **Builder notes (stage 2):** `seen_on` is the IST date the database stamped the broker row (insert or any update);
  `catalogue_contracts` keeps only expiry as a revisable column; allowlist block 8 is re-rendered by 0004 from 0002's
  text (0003's block 8 pinned the old guard and listed the moved columns) and block 9 covers `broker_instruments`;
  downgrade refuses while any catalogue row exists.
