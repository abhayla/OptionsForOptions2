# ADR-012: Market-data architecture: vendor-agnostic, shared, built for 5k to 500k users

## Owner answers
- **Q9 = B** (T1 #19): a central market-data layer feeds the website, Option Chain, strategy engine and alerts;
  broker APIs are for account/orders/execution. (Which source feeds it changed later — ADR-014.)
- Owner (T1 #175): **data is the first goal**; the owner's earlier attempt at a similar app failed on live data.
- **Q98 = C** (T2 #5): vendor-agnostic from day 1; one provider at first; replaceable, addable, fallback possible.
- Owner (T2 #101): before planning metrics, check what can **actually** be obtained, how history and changes are
  captured, and design for **5–6 thousand users growing to 100,000 and possibly 500,000**.

## Architecture (T1 #176, T2 #102)
Vendor → Market Data Gateway → Normalization → Redis/fast cache → internal event stream → Option Chain / Strategy /
Adjustment engines → platform WebSocket → browser. Browsers never talk to the vendor or hold its credentials.

## ChatGPT (delegated)
- **Q166**: Data Feasibility Test for every metric — raw data? source? can we calculate it? scale impact? historical
  availability? legal/licensing? update frequency? storage? calculation method?
- **Q167**: raw data first; derive metrics ourselves (e.g. 5-day NIFTY move = today − 5 trading days ago).
- **Q170**: shared market metrics (NIFTY 1/3/5/20-day moves, volatility measures, market-wide metrics) computed once;
  strategy metrics (P&L, net Greeks, distances, margin utilisation, IV exposure, trajectory) per active strategy.
- Greek values must be reproducible: record inputs, model, volatility, rate, timestamp, contract, and whether the
  contract was actually tradable at that time (T2 #102).
