# ADR-016: Zerodha broker boundary, contract eligibility and margin gate

## Owner answers
- Owner (T1 #57): before an order is even in progress, verify with Zerodha that enough margin is available —
  **a hard execution gate**, not a warning. Flow: fetch available margin → compute margin for the planned sequence →
  submit a leg only if enough → after each fill re-fetch Zerodha's margin → next leg. If short: *"Execution paused …
  No further order has been submitted"* + Review Strategy / Add Funds / Modify Quantity. Our figure is an estimate;
  Zerodha's is final.
- Owner (T1 #67, #69): *"Let Zerodha do the filtering"* — find out whether Zerodha allows an order for a contract and
  **only then let it into a strategy**; do not build our own checks. ChatGPT's caveats (T1 #68, #70): there is no single
  "is allowed" API; use the instrument master, what Zerodha data shows, and Zerodha's order response as final; the
  catalogue of contracts (what exists) is separate from current availability, and contracts are never deleted.
  Display: *"25,000 CE — Available ✅"* / *"27,000 CE — Currently unavailable on Zerodha ⚠️ Zerodha isn't accepting
  fresh orders for this contract right now."* Availability can be refreshed. Proposed internal statuses: valid
  contract, currently eligible, restricted, insufficient liquidity, unknown (needs broker check), order rejected.
- **Q44 = D**: an unavailable leg stays visible; alternatives offered; user picks explicitly; never silent substitution.
- Researched Zerodha facts (T1 #66, from Zerodha pages via ChatGPT, **to re-verify**): options are **not** limit-only;
  market orders are restricted for some contracts (liquidity, expiry, OI, deep ITM); **SL-M not allowed for index
  options**; orders far from theoretical price can be rejected; fresh F&O orders can be blocked by OI thresholds;
  Kite instrument dump updates daily and must not be polled.

## Broker adapter
Authenticate, fetch account, margin, positions, orders, submit order, order status, reconcile. Zerodha only.
