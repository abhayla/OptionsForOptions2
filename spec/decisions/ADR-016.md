# ADR-016: Zerodha broker boundary, eligibility, margin and broker adapter

## Decision
- Zerodha authority (Q148, Q180): account, positions, orders, margin, eligibility, order acceptance, execution.
- **Catalogue ≠ eligibility** (Q179): never permanently delete a contract. The builder avoids contracts that are
  currently unplaceable where Zerodha information allows it (15 Sep §18); there may be no single Zerodha endpoint
  that says whether every order is allowed.
- **No silent substitution** (Q127, §81): an unavailable contract stays in the version history; the problem is
  shown; alternatives may be offered; the user picks explicitly; a changed strategy becomes a new proposed version.
- Validation (§80) never silently mutates the user's strategy.
- At execution: instrument master + available pre-checks; broker response is final; never pretend to replicate RMS.
- Broker rules from past research (§43: market-order limits by liquidity/OI/expiry/deep ITM, SL-M limits on index
  options, freak-trade protection, OI and strike restrictions, basket execution) are **references to verify, not
  constants**. Never implement "options = limit only".
- **Margin** (§44): fetch available funds → compute/obtain required margin for the planned sequence → verify →
  submit only if sufficient. After fills: re-fetch state, re-check margin, continue only when dependencies hold.
  Platform estimate is planning info; Zerodha is authority. Insufficient → stop, show available vs required, allow
  quantity change / review / add funds.
- **Broker adapter** (Q181, §76): authenticate, fetch account, margin, positions, orders, submit order, order
  status, reconcile. Zerodha only; no unused broker implementations.
