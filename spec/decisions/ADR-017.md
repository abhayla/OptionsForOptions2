# ADR-017: Multi-leg execution, order handling, partial execution and no automatic retry

## Owner answers
- **Q26** (owner, T1 #55): place **buy (protective) legs first, then sell legs**, because buys free margin for the
  sells. Adopted as: Strategy → Execution Plan → Leg Dependencies → Execution Sequence → Orders; the user sees
  *Step 1 — Establish protection · Step 2 — Establish short positions* before executing; "all buys first" is not
  hard-coded for every structure (futures/naked strategies differ). Verify real Zerodha margin behaviour before
  relying on it.
- **Q27** (owner, T1 #61, confirmed #63): if a leg fails, **do not reverse** successful legs; options in this order:
  **Complete Strategy** (first), Retry Failed Leg, Review Manually, Close Partial Strategy. Before completing:
  re-fetch positions and order status, recompute the remaining strategy, re-check margin, verify the missing leg,
  submit only what is needed. Show why the leg failed. Pre-flight before starting: strategy valid, **market open**,
  contracts valid, quantity valid, margin and funds sufficient, all legs available, broker connection healthy.
- **Q28** (T1 #65–#70; owner: "for Zerodha you know the answer"): no generic Market/Limit/SL menu; a
  **Zerodha-specific execution engine** picks valid order parameters per leg (allowed types, market-order limits,
  price bands, tick size, partial fills). The user chooses *Execute at current market conditions* or *I want price
  protection* (limit / **strategy-level price tolerance**, e.g. expected credit ₹12,500, executable ₹12,350, max
  slippage ₹300 → within tolerance). A broker-specific capability matrix when more brokers come.

## ChatGPT (delegated, T2 #130)
- **Q192**: partial adjustment → explicit exception state; reconcile with Zerodha; show executed/rejected/pending,
  actual vs intended legs; recompute actual P&L, risk, margin, Greeks; no automatic compensating orders.
- **Q193**: no automatic retry in V1 (reasons: price, margin, restriction, rejection, timeout, liquidity, quantity,
  connection).
- **Q194**: order states Prepared · Submitted · Pending · Partially Executed · Executed · Rejected · Cancelled, separate
  from strategy states. **Q195**: only confirmed execution + reconciliation changes the position.

## Proposals kept (T2 #84, given under wrong numbers, content not disputed)
- A **Strategy Review** step before execution (legs, prices, max P/L, BEs, margin, charges, payoff, range, warnings,
  rules) → *Prepare Orders* builds the order plan (leg, action, instrument, quantity, order type, price, sequence,
  margin, charges, broker warnings) without placing anything → *Review Orders → Execute*.
- Changing a prepared order flows back through the strategy and recalculates risk.
- A final check just before sending: price, contract validity, margin, lot validity, restrictions, Zerodha session,
  current order/position state → *"Ready to execute · 4 orders · margin ₹X · max loss ₹Y · Execute through Zerodha"*.
- Its partial-execution action order (Retry first) is **overridden by Q27** (Complete first).
