# ADR-017: Multi-leg execution, order lifecycle, partial execution and no automatic retry

## Decision
- One user action: **Execute Strategy** → execution plan → leg dependencies → sequence → orders (§45).
- Sequence understands protection, margin impact, dependencies, broker constraints. **Not** "all buys first" for
  every strategy. Preferred default (15 Sep §21): protective/buy legs first, then the sell legs that depend on them.
- **If a protective leg fails, the sell leg that depends on it is not submitted** (15 Sep §21).
- Order states (Q194): Prepared · Submitted · Pending · Partially Executed · Executed · Rejected · Cancelled.
  Strategy state is never inferred only from orders (Q147).
- **Submitted ≠ executed** (Q195): confirm actual broker execution before changing strategy state.
- **Partial execution** (Q192, §47), e.g. 3 of 4 legs filled: explicit exception/reconciliation state; broker actual
  state wins; recalculate actual risk/P&L/margin. User options in priority: 1 Complete strategy · 2 Retry failed
  leg · 3 Review manually · 4 Close partial strategy. Never auto-unwind successful legs. Before completing:
  re-fetch positions and order status, compute the actual remaining strategy, re-check margin, verify the missing
  leg, submit only the required order(s).
- **No automatic retry in V1** (Q193): failed leg → explicit exception state, visible reason, user chooses next
  action, no hidden resubmission.
- Pre-execution safety checklist (§79): strategy valid; version active/proposed as appropriate; broker connected;
  session valid; data healthy where required; contracts valid; quantities valid; margin sufficient; dependencies
  satisfied; no unresolved reconciliation mismatch. Any failure → block, explain, log.
- **Risk UX (Q124, §28):** no repetitive generic "I understand the risks" checkbox. Normal risk → explain;
  elevated → warn; exceptional → explicit acknowledgement. The execution review shows strategy, margin, max loss,
  max profit, current P&L, leg count, execution sequence and broker.
