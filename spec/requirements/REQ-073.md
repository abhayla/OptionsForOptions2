# REQ-073: Orders through Kite's own order page

Why: NSE counts every order sent through a broker API as an algo order (F-17) and wants algo providers' strategies run
on the broker's servers (F-18); Zerodha's offsite execution sends users to "Kite's exchange approved order page where
they place orders" (F-22).

Example: an Iron Condor's exit plan has 4 orders. The user presses Execute Strategy, Kite's page opens with the 4
orders locked, the user places them, and returns; we read Zerodha's order book by our tag and reconcile.

AC-4 clarification (owner, 2026-10-16 ~08:00 IST, with the question tool): every Kite HTTP request goes through one door
that checks the host and path against the allow-list before anything is sent; a web address whose host holds any
non-ASCII character is refused outright, never converted and compared (for example `api。kite。trade` with U+3002
dots, which Python's HTTP libraries would deliver to `api.kite.trade`). Every module that calls Kite is named in the
allow-list with its calls, including the margin reads (`GET /user/margins`, `POST /margins/basket`).

AC-4 scope (owner, 2026-10-16 ~15:45 IST, ADR-098): AC-4 is met when every route open to ordinary code is refused at
runtime or flagged by the scan. Out of scope: ctypes/cffi, computed-name reflection, gc, changing the hook's state,
native-code event loops, and deliberately forged code objects (a forged co_filename through any compiler, e.g.
`codeop.compile_command(src, "<path in a trusted library>")`). The runtime gate is installed by create_app() and by
importing any Kite door module, so every process that can reach Kite is gated; tool processes that load no door are
not (technical clarification, ADR-098).

AC-3 return path (F-41, 2026-10-17): Kite sends the browser back from a basket to the same registered redirect URL as
login; a return that carries no login state lands on a page offering only "Check with Zerodha", which never runs the
return by itself and never shows a login error. The live return shape is confirmed at the first real basket.

AC-1 two-basket entry (owner, 2026-10-19, ADR-117): when any sell depends on a protective buy, an entry is TWO baskets,
each one read-only and in plan order as AC-1 says: basket 1 the protective buys, then "Check with Zerodha" (AC-3)
confirms the fills, then basket 2 the sells. A strategy with no such dependency stays one basket. Kite is never
re-opened for a basket whose tagged orders already exist (AC-2 tags stay unique per basket).

Decisions: ADR-054. Open: Q259 (Zerodha's confirmation; basket size limit and how a rejected leg is reported).
