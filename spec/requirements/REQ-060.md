# REQ-060: Reconciliation with Zerodha

Platform state is continuously reconciled with Zerodha; broker state wins; mismatches block execution.

Decisions: ADR-018. Sources: M §49, §78; C-file (real Q numbers: spec/traceability/question-register.md).

**Owner decision (2026-10-15, Q269, ADR-083):** a leg whose contract has expired is closed in the platform at the
settlement price as a recorded event after the expiry close; reconciliation expects it gone and does not raise AC-2's
"missing platform position" for it.

**Clarification (2026-10-16, issue #279, applying ADR-083 to AC-7; owner to confirm, OQ-8):** a quantity recorded as
standalone (AC-7) on a contract that has expired and that Zerodha no longer shows is not a mismatch either: it gets a
one-time, non-blocking note (`RECONCILIATION_MISMATCH_221`) and the standalone record is retired, so the note is
not repeated once the caller saves the retired map (persistence: #279 item 4). An expired contract on which Zerodha
still shows a quantity different from the platform's record is labelled as that (`RECONCILIATION_MISMATCH_222`)
instead of "missing" or "side"; it blocks exactly the strategies it blocked before.

**Open:** Periodic reconciliation after the daily session expires: Q205. See `spec/open-questions.md`.

**Delegated overnight decisions (ADR-045, reversible):** Q222 — an agreeing run does not unblock by itself; a recorded manual resolution is needed. Q224 (SPEC CHANGE for shared contracts only) — when a contract held by two or more strategies disagrees with Zerodha, adopt / prepared closing order / broker flat → exited are refused and every holder stays blocked, because the spec defines no attribution across strategies. See `spec/open-questions.md`.

## Owner confirmation (2026-09-29): Q222 and Q224 stand
- Q222: an agreeing reconciliation run does not unblock a strategy by itself; the block lifts only through a recorded
  manual resolution. Q224: a contract held by more than one strategy that disagrees with Zerodha blocks every holder
  and refuses guess-based fixes; the user resolves by trading in Kite and re-running. Both were delegated overnight
  (ADR-045) and are now confirmed by the owner; no longer "reversible pending review".

## Owner decision (2026-10-18, ADR-109): app-owned lots; first reconcile screen
- A strategy owns exactly the fills of orders this app placed (its order ids and tags, ADR-105). Per contract, a
  same-direction surplus at Zerodha beyond every strategy's own fills plus the recorded standalone quantity is shown as
  outside lots and blocks no strategy (clarifies AC-4 and AC-7). A shortfall still blocks (AC-6, unchanged). Examples:
  strategy BUY 65 CE, Zerodha 130 -> not blocked, 65 outside; strategy 65 + standalone 25, Zerodha 90 -> no
  mismatch; Zerodha 0 -> blocked.
- The user may attach outside lots to a strategy or detach them by a recorded action (a later release).
- The first reconcile screen (AC-5) offers three actions: close/reconcile through a prepared basket, mark as requiring
  attention, Zerodha flat -> mark exited. Adopt and Review and modify come later.

## Design (2026-10-19, #380-1 review): which resolution lifts a block
- Only a resolution that settles the position lifts the block (ADR-018 Q198: no casual "ignore"; Q222: the block
  lifts only through a recorded resolution). Two do: a prepared basket that reconciled it, and Zerodha flat -> mark
  exited, which needs Zerodha's net for that contract to be 0 in the positions read for that action, not the net
  recorded earlier. "Mark as requiring attention" is recorded for the audit and does not lift the block; the mismatch
  can still be settled afterwards.
- A contract on which another strategy of the same user also has an unresolved mismatch is shared (Q224): both
  settling actions are refused and every holder stays blocked.
- An unresolved ENTRY plan's real lots are never left unaccounted: the plan may close as unresolved only when a
  mismatch is recorded for the strategy, and no remaining resolution lifts that block while Zerodha still shows the
  lots.

## Findings (spec/findings.md, 2026-10-02)
- F-07: Zerodha postbacks cover only orders placed with our API key, while the websocket order feed covers all of a
  user's orders (including orders placed in Kite or other apps); detecting external changes (AC-2, AC-4) needs the
  websocket feed plus polling, not postbacks alone.
- F-08: comparable platforms record orders found at the broker but unknown locally as external rather than dropping
  them, and reconcile at startup before acting - consistent with AC-4 and AC-6.
