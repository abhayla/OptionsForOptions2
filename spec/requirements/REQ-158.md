- id: AC-3
  text: >-
    A user may create, duplicate, rename and delete any number of named playbooks per type; a name is unique within a
    type, and a duplicate name is refused with "A playbook named <name> already exists for <type>".
- id: AC-4
  text: >-
    Exactly one playbook is active per type for each user; making one active makes the previous one inactive. Deleting
    the active playbook makes the type's system playbook active and says so.
- id: AC-5
  text: >-
    Precedence: the strategy's own plan, then the playbook chosen for it, then the type's system playbook (REQ-045
    AC-7). Deleting or editing a playbook never changes a strategy already tracking: that strategy keeps its own plan.
- id: AC-6
  text: >-
    A system playbook can only be saved as a new playbook; the user's own playbook can also be saved in place ("Save
    changes").
- id: AC-7
  text: >-
    Every playbook value is stored data, not code, so a value changes without a release (catalogue Part 9c). An item
    that cannot apply to a type is kept and shown greyed with its reason, for example "Add wings" on an iron condor:
    "loss already capped"; it is never dropped.

# REQ-158: Playbooks - store and resolution

Why: the owner wants the full rule set of the catalogue on every strategy family, with a system playbook per type and
the user's own named playbooks, one active at a time (ADR-214 (4a), (4b)).

Decisions: ADR-214.
