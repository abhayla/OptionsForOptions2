# Lanes (parallel cloud sessions)

A lane is one cloud session with one goal, one branch and a fixed list of files it may edit. The coordinator is the
session that talks to the owner and runs the lanes. These rules come from the owner's instructions of 25 to 27 Nov
2026. Times are in the owner's time zone (IST).

## Standing rules for every lane
A brief names this section on its first line and does not repeat it. Read it before your first command.

**Time and pace**
- Times in IST; run `TZ=Asia/Kolkata date` before you stamp one (a guessed clock was wrong by 5 to 30 minutes).
- Work continuously through the queue; never wait for the coordinator. Stop only at the Budget, at a real blocker
  (owner-only credential, spend, production deploy, irreversible step, true product fork) or when the queue is empty.
- At most two rounds per item, then park it: say what is left and move on.

**Read first (in this order)**: `CLAUDE.md`; `docs/process/standing-direction.md`; this section; the newest
`docs/process/session-handover-*.md`; `docs/process/runbook.md` ("Lanes", "Before a push"); the ADRs the brief cites.

**Files**
- One file, one lane. Edit only the brief's `May edit:` files. If a fix needs another lane's file, do not edit it:
  write the exact change under "For the owner lane" in RESULTS.
- Do not pick decision numbers; the coordinator hands them out.
- No migration unless the brief says so.

**Product rules (never break)**
- Paper equals real (ADR-330 (58)): a paper path uses the same rules and sentences as the real one.
- Never call a broker order endpoint; a lane can lose real money.
- Money is exact `Decimal`, never float (ADR-008). One module per capability. Decision-support wording, never advice.
- New on-screen sentences are listed in RESULTS as "pending owner read" (the owner approves the words).

**How to build**
- Test first, and cover every answer state (stated, absent, not found, failed, empty, ambiguous).
- No waste: targeted tests, long output to a log file and only its tail read, no re-reading of what you already know.
- Models: Sonnet builds and runs tests; Haiku does mechanical work (counts, logs, regenerating, merges); Opus only for a
  named Tier A review of a money, stop, exit or price path (brief says `Why Opus:`). The task picks the model, never
  the session's default. Every helper brief carries `Budget: <N> min wall-clock, <M> tool calls`. RESULTS has a table
  `task / model / minutes`.

**Gate and git**
- Before a push: `env -u HTTPS_PROXY -u HTTP_PROXY -u https_proxy -u http_proxy -u ALL_PROXY -u all_proxy
  -u TEST_DATABASE_URL -u TEST_ADMIN_DATABASE_URL -u ALEMBIC_DATABASE_URL -u OFO_REQUIRE_DB_TESTS
  python scripts/orchestrator/prepush.py` must end `TOTAL PASS` on a clean tree (the proxy breaks the local test
  servers). Never set `PREPUSH_GATE_ALLOW`. Generated files are regenerated by their tool, never by hand.
- `ruff` is at `/root/.local/bin`. `git add`, `git commit` and `git push` are three separate calls.
- Push only to the lane's own branch; no PR unless the owner asked; never main or the test branch.
- Do not file GitHub issues; list them under "To file as deferred issues" (the coordinator files them once).
- No private link, server address, login or key path in the repo, a commit or a PR (the repo is public).

**Status and report**
- The highest status you may claim is "Fixed, not tested". Give PC steps twice: for market closed and for live.
- RESULTS file `docs/design/next-batch-2026-11-26/RESULTS-lane-<x>.md`, with a line at the very top:
  `STATUS HH:MM | item: state | next push HH:MM | blocker: none`.
- Send one line to "@parent" at start, at each push and when done. If it is refused, the STATUS line on the pushed
  branch is the report (push it early).
- When the queue is done write `SAFE TO CLOSE (head <sha>, what is left)` and stop.

## Roles
- The coordinator only asks, splits, routes, verifies and reports; it builds nothing, runs no tests and does no
  mechanical work (its context is the one thing every lane depends on).
- A lane does one goal on its own branch and reports in the fixed line (the coordinator reads one line, not a
  transcript).
- The owner answers business questions, types approvals, and archives finished lanes (only he can for a device-bound
  lane). Technical and architectural calls are the coordinator's, never the owner's.

## Starting a lane (the brief)
Every brief is self-contained: the lane does not see the coordinator's conversation. Copy `brief-template.md` and fill
only what differs for this lane: who you are, Budget, branch and base, files owned and not owned, the queue with real
cases and the decision texts, reviews required, pushes, core and proof. Then run
`python .claude/skills/lanes/check_brief.py <brief-file>`; it fails on a missing part and on a brief that repeats the
standing rules (more than 15 such lines). A passing example: `examples/brief-lane-k.md`.
- Where the project has a broker, the standing rule "never call a broker order endpoint" applies; do not restate it.
- Use `Model:` and `Why Opus:` only where the lane's model differs from the standing table.

## Models (why)
- Haiku for mechanical work (nothing to judge), Sonnet for building and tests (enough skill, a fraction of the cost),
  Opus only for an independent review where a wrong answer costs real money (it is the scarce model).
- A lane whose whole job is wording or documents starts on Sonnet; a lane on stops, exits, prices or money starts on
  Opus. Never use the coordinator's own top model for code work (it must stay free to coordinate).

## Context
- Give a finished lane a next task in the same session only when it is a related follow-up in the same code.
- Send an unrelated task to a FRESH lane with a self-contained brief; never stack unrelated work on an old context.
- A finished lane reports `SAFE TO CLOSE (head <sha>, what is left)` and the owner archives it (archiving deletes the
  machine, so the push must be confirmed first).
- Queue each lane's next related task before it finishes, so no lane sits idle.
- Give every item an owner lane; an item without one is never started.
- Check every lane each time any lane or the test machine reports (one report often unblocks or invalidates another).

## Reporting (coordinator side)
- One line per push: `head <sha> | gate <result> | re-test <what>`.
- Read the branch; never state a lane's status without having looked at its branch or session that minute.
- Another session's report is a claim: re-read the artifact first (branch head, log line, database row).
- Write times in IST in plain words, bad news first, no repeated messages (the owner reads on a phone).
- Run `python -m pytest tests -m repo_scan -q` before the gate when the gate has not been adopted in a lane (a gate run
  is long; a failure found early costs minutes). A lane on the faster gate (`chore/gate-speed-1127`) needs no
  separate pre-check.

## Files and branches
- Split by files, not by bug: two bugs in one file go to one lane.
- A shared piece is built by one lane and adopted by the others (one version of the truth).
- One branch per lane, cut from the same commit; merge, never rebase or force-push a branch another session uses.

## Approvals and permissions
- Expect a lane's safety check to refuse edits to oversight files (gates, allow-lists, review notes, standing
  direction) unless the owner types the approval into that lane himself.
- A refused edit: the lane stops that edit, writes at the very top of RESULTS one paste block
  `OWNER APPROVAL NEEDED: <exact file and change>`, and goes on; it never works around the refusal.
- Bring the owner one paste block per lane, early, never after a failed gate (he can answer once, not after a lost
  35 minutes).
- After a worker restart, tell the owner to set Auto mode again.
- Do not try to archive or read the transcript of a device-bound lane: ask for SAFE TO CLOSE and the owner archives.

## Questions to the owner
- Ask only business or functional questions, one at a time, alone in the message (mixed messages get half answers).
- Look the subject up first (`docs/process/owner-decisions-by-subject-2026-11-26.md` and the spec) and never ask the
  same subject twice.
- Write the decision row the same turn an answer arrives (an answer with no row is lost at the next restart).
- When the owner is away or has given authority: decide the spec-conformant choice, record it with its reason and list
  it for his review. Do not hold work for an answer; start what needs none.

## A live test day
- Prepare the evening before: set-up (backup, migrations, restart), final plan, start message, login steps; build
  nothing while the market is open.
- Run everything that needs no live market before it opens (market hours are short and cannot be repeated).
- The test machine tests as a user in the browser, critical checks first; run two tracks when one cannot finish.
- Never wait on the market: set levels so they trigger. Never skip a check because a helper's budget is low.
- Status every 15 minutes in a short fixed shape: changed rows only, in complete sentences. Refresh the status page
  every 15 minutes (it is what the owner opens first).
- One list of every issue found, with criticality, dependency and owner lane. Usability notes go on a separate list and
  are not acted on that day.
- Fix a blocker at once on its own small branch cut from the tested head; a fix touching money, stops, exits or prices
  is reviewed, then gated.
- Pull a fix into the test machine with a written PULL order: merge, build only if the frontend changed, restart only
  what changed, measure before and after, and the re-run list. Use one restart for several fixes where possible.

## Closing a lane
1. The lane pushes its last commit and its results file, with the `task / model / minutes` table.
2. The lane reports `SAFE TO CLOSE (head <sha>, what is left)`; the coordinator re-reads the branch head on GitHub.
3. The coordinator files the lane's `To file as deferred issues` list once.
4. If a related follow-up exists in the same code, queue it in that session; otherwise start a fresh lane.
5. The owner archives the lane after the push is confirmed.
